# 07. 팀과 문서

## 일정

- 마감은 시스템 마감보다 반나절 앞에. 기능 동결일, 기준선 태그(v1.0.0), 제출본 태그(v1.1.0)를 처음 일정표에 넣는다.
- 동결 뒤에는 치명적 오류와 문서만. 개선 아이디어는 다음 단계 라벨(예: `next`)로 모은다.
- 이슈 우선순위는 P0(서비스가 멈춤, 오늘) / P1(마감 전) / P2(여유 있을 때).
- 서비스가 멈추는 긴급 오류는 팀장이 먼저 고치고 담당자가 사후 리뷰한다.

## 할 일 관리 (노션 등)

- 페이지 맨 위에 "지금 상황" 한 줄, 그 아래 일정표(언제, 누가, 무엇을).
- 항목마다 담당, 마감, 완료 기준, 근거 링크. 끝난 일은 체크와 취소선, 결과 링크.
- 팀방 공지와 같은 체크리스트 페이지를 따로 두고 둘을 같이 갱신한다.

## 회의

- 30분, 길어도 1시간. 혼자나 1:1로 풀 수 있는 것은 안건에서 뺀다.
- 형식: 타임라인 표 + 안건별 핵심, 논의, 아이디어 후보 + Done / Todo / Discuss + 실시간 메모([templates/meeting-notes.md](../templates/meeting-notes.md)).
- 의견이 안 나오면 A/B/C 시안 + "몇 시까지 의견 없으면 A로" 같은 침묵 방지 문장.

## 팀에 보내는 글

- 짧게, 사실과 다음 행동만. 팀방이 반말이면 문구도 반말.
- 팀 산출물(이슈, 문서, 보고서)에 사람을 평가하는 말을 쓰지 않는다. 고칠 점은 PR 리뷰로.
- 팀원 결과물은 갈아엎지 않고 기반으로 삼아 고친다.
- 다른 팀이나 조직의 자료를 참고했으면 이름 대신 "참고 자료"로. 도구와 데이터 출처 이름은 쓴다.
- 남의 이름으로 메시지나 댓글을 대신 달지 않는다(문안만 만든다).

## 인수인계

- 채팅이 길어지면 [templates/handoff-chat.md](../templates/handoff-chat.md)로 문서를 만들어 프로젝트 문서에 저장하고 새 채팅을 연다.
- 다른 프로젝트로 넘길 때는 이 레포(`JHarvis`)를 넣고 프로젝트 고유 사실만 인수인계 문서에 쓴다.

## 제출

- 제출물 체크리스트: 파일 이름 규칙(예: `학과_이름(학번)`), 형식(양식 확장자 유지), 용량, 입력 칸 기본값 확인(예: 논문/작품, 개인/공동), 제출 후 화면 캡처.
- 시스템 오류 대비: 브라우저 바꾸기 → 담당 부서 전화 → 마감 전 이메일 제출(공지에 있으면).
