# 05. 정직한 결과와 발표

## 숫자

- 지표는 원래 이름 그대로. ROC-AUC는 정확도나 적중률이 아니다.
- 쉬운 말로 풀 때도 정확하게: "100쌍 중 약 57쌍에서 상승 쪽 점수가 높았다".
- 지표 선택 기준: 누구나 이해할 수 있고, 정확하고, 다시 계산할 수 있을 것. 근거 문서를 남긴다.
- 오해를 부르는 지표는 높아 보여도 뺀다(모두 "아님"이라 답해도 높게 나오는 일치율).
- 결과 수치는 표 하나(SSOT)에 모으고, 보고서, 발표, 화면이 같은 값을 쓴다.
- 보고서 수치에는 출처(문서, PR, 실험 결과 파일)를 붙인다.

## 실험

- 시작 전에 비교 조건(같은 표본, 같은 시드, 같은 평가 함수)과 판정 기준을 적는다.
- 효과가 없으면 없다고 쓴다. 좋은 숫자만 고르지 않는다. 표본이 다른 두 결과를 순수 효과로 비교하지 않는다.
- 범용 점수보다 "우리 업무 기준"으로 모델을 고른다(예측 지표가 올라도 실제 쓰임새의 성과가 떨어지면 채택하지 않는다).
- 사실의 수준을 나눈다: 확인된 사실 / 당시 기록 / 해석 / 미확인.
- 계산 오류를 찾으면 값을 지우지 않고 무효로 표시하고 이유를 남긴다. 표본 기준에 못 미치면 화면에 넣지 않는다.
- 지표 근거 문서 양식: [templates/research/metric-choice.md](../templates/research/metric-choice.md).

## 사용자 평가

- 결과표에 누가, 언제, 어떤 방식인지 칸으로. AI 페르소나 워크스루는 사전 점검으로 따로 적고 실제 평가 횟수에 넣지 않는다.
- 대표 의견 → 반영 내용 → PR 번호로 이어지게 적는다.
- 양식: [사용성 테스트 계획](../templates/research/usability-test-plan.md), [AI 페르소나 워크스루](../templates/research/persona-walkthrough.md).

## 발표와 질의응답

- 발표 수치는 출처와 사실 여부를 담당자와 미리 확인한다.
- 발표 전 채팅 Claude에게 "심사위원이 공격할 질문 10개와 답"을 시킨다(스트레스 테스트).
- 한계를 먼저 말하고 다음 단계로 잇는다: "왜 한계를 느꼈나 → 무엇을 더 검증하나".

## 보고서

- 장마다 첫 문단에 결론 한 문장. 주장마다 숫자, 날짜, PR 번호 중 하나.
- 계획 대비 결과 표(신청서의 단계 그대로)와 "달라진 점과 이유" 칸.
- AI 티 나는 문장 금지: 꾸밈말, "~를 통해", "~라고 할 수 있다", 목록 남발.
- 개인 기여는 "무엇이 막혔고 어떻게 풀었나" + 근거(PR 번호, API 집계).
