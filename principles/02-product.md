# 02. 제품 설계 원칙

어떤 도메인에도 옮길 수 있게 일반화한 원칙입니다. 괄호는 원래 사례.

## 출발점

- 기능에서 문제를 찾지 않고 문제에서 기능으로 간다. 대상 사용자의 문제를 공개 자료로 정리하고, 운영 화면을 열어 해결 정도를 판정한다([templates/research/problem-feature-map.md](../templates/research/problem-feature-map.md)).

## 다섯 가지 기본

1. **화이트박스**: 모든 점수와 문장은 어떤 데이터와 규칙에서 나왔는지 설명할 수 있어야 한다. "AI가 그렇게 판단했다"는 답이 아니다.
2. **결정론**: 점수, 순위, 경고 조건은 같은 입력에 같은 출력이 나오는 코드로. LLM은 설명 문장에만. 채점 규칙은 골든 케이스로 고정한다.
3. **하드 제약 / 소프트 틸트**: 사용자가 직접 정한 것만 결과를 지운다. 모델과 성향 점수는 순서, 강조, 임계값에만 쓴다. 애매하면 "사용자가 직접 체크했나?" 하나로 판정.
4. **사람이 판단**: 자동 실행(매매, 결제, 발송)을 하지 않는다. 선택지와 근거를 보여 주고 결정은 사용자에게 남긴다. 지시 대신 "미리 합의한 기준에 닿았다"는 사실만 알린다.
5. **재현성**: 시드 고정, 공용 평가 함수 하나. 모델마다 자기 평가 코드를 따로 두지 않는다.

## 표현 규칙

- 단정 금지: "오를 확률 70%" 대신 "과거 비슷한 경우 N번 중 M번".
- 근거는 두 단으로: **필요성**(사용자 조건에서 무엇이 부족한가) → **기대 역할**(이 항목이 그 부족분에서 무엇을 맡나).
- 투자 권유, 의료 진단처럼 규제가 있는 영역은 금지어를 코드 검사로 막는다("추천" 등).
- 같은 대상은 끝까지 한 이름.

## 데이터

- 외부 데이터마다 약관 네 칸: 자동 수집 가능? AI 입력 가능? 보관 기한? 무료 한도?
- 후보 공급원은 실측(건수, 관련성 비율)으로 고른다. 기준을 먼저 정한다(예: 3건 이상, 관련성 80% 이상).
- 값이 없으면 0이 아니라 결측. 없는 데이터를 만들어 채우지 않는다. 예시 값은 "예시"라고 표시한다.
- 자동 갱신: 적재와 게시 분리(검증 통과분만 공개), 실패 시 직전 게시본 유지, 늦으면 "며칠 전 데이터" 표시, 예비 실행.

## 블록과 계약

- 팀이면 블록(담당 영역)마다 입력과 출력을 JSON 스키마와 예시 파일로 적고 동결한다. 바꿀 때는 `[schema]` 제목과 전원 합의.
- 블록 결과는 마지막에 합치고(late fusion), 시간 지평이 다른 블록은 먼저 맞춘다.
- 따로 자란 블록을 붙이기 전에 읽기 전용으로 [통합 지도](../templates/integration-map.md)를 만든다.
- 필드명에 단위를 넣는다(`target_return_pct`). 통계 지표는 파라미터를 응답에 함께 싣고 라벨은 파라미터에서 만든다.
- 화면이 DB를 직접 읽는 구조(별도 API 서버 없음)라면 DB 스키마가 곧 API 계약이다. 행 단위 보안(RLS)을 같은 마이그레이션에서 켠다.

## LLM과 RAG

- 결정론, LLM, 사람(확정)의 세 계층으로 나누고 LLM 호출 지점 수를 문서에 숫자로 적는다.
- RAG는 해석과 근거 문장에만, 첫 버전은 RAG 없이. 숫자, 세율, 상품 매핑은 규칙표나 코드로. 후보마다 "이게 바뀌면 누가 어디를 고치나"를 묻는다.
- 문서를 바꾸면 인덱스를 통째로 다시 만들고, 새 문자열 검색과 옛 문자열 부재를 확인한다.
- 사람 승인이 있으면 첫날 [상태 전이표](../templates/state-transitions.md)를 만든다. 실패하면 멈추고(fail-closed), 규칙 숫자는 코드 한 곳에만 둔다([규칙 문서](../templates/hard-stop-rules.md)).

## 콜드 스타트

- 사용자가 쌓여야 되는 기능(남들과 비교)은 첫 버전에서 공개 데이터나 자기 참조형으로 바꾼다.
